### 1.2 ⚠ 基線文件的數字不具代表性——這點要更正

`docs/perf-baseline-2026-08-17.md` 記的「全部 phase 合計約 50–58 ms/60 秒」是取樣自安靜視窗。
把 log 裡改動前所有 `slots=13` 的視窗（n=93）攤開，真實分佈是：

```
改動前 (n=93)   合計 min/median/max =  5.6 / 83.4 / 167.9 ms per 60s
改動後 (n=10)   合計 min/median/max = 10.2 / 62.9 / 115.2 ms per 60s
```

**改動前的實際最大值 167.9ms 本身就超過了文件自訂的 150ms 紅線。**
也就是說：拿 50–58ms 當基準去說「改後變兩倍」是不成立的，改後的分佈反而落在改前分佈之內。
下次要做效能驗收，基線必須記分佈（min/median/max + n），不能記單一視窗。

同理，**RD 宣稱的「改後 10.2/24.3ms/60s」也是取自安靜視窗**，不能拿來當結論；

## 2. SA 標記的最大風險：重複洗版 —— **已重現**

### Blocker B-1：飽和分頁的 64 行重掃造成同一段內容重複轉發（0 → 64 次）

SA A8 風險表：「P0-2 掃描 history 尾端 64 行，可能重抽舊內容 → 重複轉發。
**完全依賴 `sent_responses`**」。RD 的實作註解（`:715-717`）也自承
「集合不可靠就會把『靜默丟訊』換成『隨機重複洗版』」。

**去重集合本身沒問題**——`_OrderedSet` 保序正確、溢位裁切（200→100，`:1982`）
我刻意攻擊過也沒破（見 §2.2）。**問題出在 superset 規則。**

#### 機制

`_extract_new_text` 的 AI block 會把 `⏺` 之後的所有行一路收集到遇見提示符為止。
飽和分頁每次重掃尾端 64 行時，block 都會多吃進上一輪新增的那幾行 →
**每輪產生一份比上輪更長的文字**。接著撞上 `:1929-1938` 的 superset 規則：

```python
if prev in text:
    supersets.append(prev)      # 判定為「更長的版本」
...
for prev in supersets:
    slot.sent_responses.discard(prev)   # 把舊的短版本從去重集合裡拿掉 → 送新的
```

於是每一輪都被判定成「這是加長版，該送」。去重集合完全沒有機會擋。

#### 重現（`qa_dup_realistic.py`，飽和 slot，140 輪）

| 分頁輸出形狀 | 改動前 | v0.29.33 | 判定 |
|---|---|---|---|
| 情境 1：Claude Code TUI，每次重繪帶 `›` 輸入框 | 0 | **1** | ✅ 修對了 |
| 情境 3：TUI 工具結果 `⎿` 連續捲動 | 0 | **1** | ✅ 修對了 |
| 情境 2：純捲動輸出（shell 分頁 / build / 長 log，無提示行）| 0 | **64** | ❌ 洗版 |

情境 2 的 64 則長度為 799, 806, 813, 820, 827, 834…（每則遞增一行），
`qa_dup_ab.py` 另一組測資累計 12721 字元。

#### 觸發前提（精確）

1. 分頁 history deque 已飽和（`maxlen=800`，長壽命分頁必然滿足）
2. 輸出形狀是「沒有提示行終結 AI block」的純捲動文字
3. **連續輸出超過 120 秒** —— `:2991` 的閘門 `if idle < 3.0 and total < 120.0: continue`
   在 total ≥ 120s 之後就被繞過，此後每個 0.5s tick 都會進來（RD 自己的註解也寫明了）

長 build、`tail -f`、訓練 log、大量 diff 輸出的 shell 分頁都符合。

#### 連鎖後果

洗版 → TG 回 429 → 走 P0-3 新增的失敗路徑 → 觸發 M-4 的**無節流** ⚠ 警告，
再加上 `_send_text_checked` 的重試（20s × 2 + inline `sleep(≤5s)`）都在**單執行緒的 flush loop 裡**
→ 所有分頁的 TG 收送一起卡住。這條鏈才是真正會「搞掛」的部分。

#### 建議修法（不在本次驗收範圍內施作）

superset 規則在「內容還在持續增長」時不該觸發。可行方向：block 尾端仍在增長
（本輪 text 的前綴等於上輪、且 slot 仍在輸出）時視為未完成，不轉發也不動去重集合；
或對飽和重掃路徑關閉 superset 展開、只做精確比對。

### 2.2 `_OrderedSet` 裁切邊界 —— 攻擊未破

刻意攻擊「超過上限時丟舊的，會不會把還會被重抽到的舊內容丟出去」：

- `qa_attack.py::a2_cap_eviction_resend`：260 個單行 block → 重送 0
- `qa_attack2.py::b2_cap_eviction`：400 個單行 block，dedup 峰值 150 → 重送 0

原因是設計上留了餘裕：保留量 100 筆 > 重掃窗（64 history + 50 display，且多行 block 只算一筆）。
**這一項 RD 做對了，SA 擔心的裁切問題不存在。**

保序性也驗過（`a5_orderedset`）：`_OrderedSet(["a","b","c"])` 經 add/discard/重複 add
後為 `["a","c","d"]`，符合預期；reload 後被還原成 plain set 時，`:1770` 的
`isinstance` 正規化確實會轉回 `_OrderedSet`。
